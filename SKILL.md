# SEO Article Writer

> **Публичная версия** — настрой свои проекты через онбординг (раздел "ОНБОРДИНГ НОВОГО ПРОЕКТА").
> Таблицы маршрутизации площадок и продуктов пустые — добавь свои проекты через онбординг или вручную.

Пишем статьи, которые попадают в ТОП Яндекса и Google и выбивают конкурентов. С реальными скриншотами сервисов и AI-иллюстрациями.

> **ГЛОБАЛЬНОЕ ПРАВИЛО: НИКОГДА не открывай изображения через Read tool без предварительной валидации!**
> Битый файл в контексте вызывает API Error "Could not process image" и убивает весь разговор — восстановить невозможно.
> **Перед КАЖДЫМ Read для изображения:** `file /tmp/img.png` (должно быть "image data") + `ls -la` (>10KB).
> Если валидация не прошла — НЕ читай файл, а пересними/перегенерируй.

## Входные данные от пользователя

При запросе на написание статьи пользователь может передать:

**Вариант А — только тема:**
> «Напиши SEO-статью про AI-дизайн интерьера»

В этом случае Claude сам определяет угол, структуру и тональность на основе анализа конкурентов.

**Вариант Б — тема + направление:**
> «Напиши SEO-статью про AI-дизайн интерьера. Статья должна быть в духе практического гайда для людей которые делают ремонт, без воды, с конкретными инструментами и ценами. Акцент на том что это доступно даже без дизайнера.»

Направление может включать:
- Тональность (экспертная / дружелюбная / провокационная / нейтральная)
- Целевая аудитория (новички / профессионалы / владельцы бизнеса)
- Угол подачи (практический гайд / обзор / кейс / сравнение)
- Акценты (на что делать упор в тексте)
- Что исключить (чего не писать)
- Стиль (с юмором / строго / с личным опытом)

**Правило:** направление от пользователя — приоритет над анализом конкурентов. Если пользователь сказал «без воды» — никакой воды, даже если все конкуренты пишут развёрнуто. Если сказал «для новичков» — никакого профессионального жаргона без объяснений.

Перед началом работы явно зафиксируй что понял:
```
ТЕМА: [тема]
НАПРАВЛЕНИЕ: [направление или "определяю по анализу конкурентов"]
АУДИТОРИЯ: [аудитория]
ФОРМАТ: [гайд / обзор / кейс / сравнение]
```

## ОПРЕДЕЛЕНИЕ ПЛОЩАДКИ И ПРОДУКТА (ОБЯЗАТЕЛЬНЫЙ ШАГ)

Площадка (куда публиковать) и продукт (что продвигать) — это **два независимых параметра**.

> **КРИТИЧЕСКОЕ ПРАВИЛО: «Дзен» != «Блог»**
> - Пользователь говорит **«Дзен»** — площадка `dzen-*.md`, публикация через **WordPress API** (blog.xxx.ru -> RSS -> Яндекс.Дзен)
> - Пользователь говорит **«блог»** — площадка `blog-*.md`, публикация через **Prisma Blog API** (xxx.ru/blog), формат **MDX**
> - Это РАЗНЫЕ системы, РАЗНЫЕ API, РАЗНЫЕ форматы. НИКОГДА не путать.
> - Если непонятно — СПРОСИТЬ: «В Дзен (WordPress) или в блог на сайте (Prisma)?»

### Шаг 1: Определи площадку

По запросу пользователя найди файл площадки в `projects/platforms/`:

Прочитай файл площадки -> возьми WP-переменные и UTM.

### Шаг 2: Определи продукт

1. Если в промпте **явно указан продукт** (например «про МойПродукт») -> используй его
2. Если нет — проверь поле **«Продукт по умолчанию»** в файле площадки
3. Если продукта по умолчанию нет -> **спроси пользователя:** «Какой продукт продвигаем в этой статье?»

Продукты находятся в `projects/products/`:

Прочитай файл продукта -> возьми название, URL, фичи, тарифы, правила упоминания.

### Шаг 3: Зафиксируй

```
ПЛОЩАДКА: [название] -> [файл площадки]
ПРОДУКТ: [название] -> [файл продукта]
WP: [переменные из площадки]
САЙТ: [URL из продукта]
```

**Правило первой ссылки:** Первое упоминание продвигаемого продукта со ссылкой ДОЛЖНО быть во 2-3 абзаце статьи (вступительный блок). Не откладывай первую ссылку до середины текста.

## ОНБОРДИНГ НОВОГО ПРОЕКТА

Триггеры: «добавь продукт», «новый проект», «создай профиль», «подключи сайт».

Когда пользователь хочет добавить новый продукт или площадку — выполни этот маршрут. Он собирает всю информацию автоматически и создаёт готовые профили.

### Шаг О1: Уточни у пользователя

Спроси (если не указано в промпте):

**Базовое:**
```
1. URL сайта продукта (например: myproduct.ru)
2. Название продукта (например: МойПродукт)
3. Есть ли площадка для публикации? Если да:
   - Название площадки (например: Дзен МойПродукт)
   - URL блога (например: blog.myproduct.ru)
   - WP-переменные уже настроены в config.env? Если нет — какие имена использовать?
4. Эта площадка привязана к этому продукту по умолчанию? (да/нет)
```

**О продукте (экспертная информация от пользователя):**
```
5. Расскажи своими словами: что делает продукт, для кого он, в чём главная ценность?
6. Какие ключевые фичи/функции выделить в статьях?
7. В чём главные преимущества перед конкурентами?
8. Есть ли особенности: бесплатный план, пробный период, ограничения?
9. Как хочешь чтобы продукт упоминался в статьях — нативно как один из инструментов, или как основной герой?
10. Есть ли что-то, что НЕ надо писать о продукте? (ограничения, слабые стороны, которые не стоит акцентировать)
```

**О конкурентах:**
```
11. Кто основные конкуренты? (URL-ы, если знаешь)
12. Чем ваш продукт лучше каждого из них?
13. Есть ли конкуренты которых НЕ стоит упоминать в статьях?
```

Не обязательно спрашивать всё — если пользователь дал развёрнутый промпт, часть ответов уже есть. Спрашивай только то, чего не хватает.

### Шаг О2: Разведка сайта

Автоматически собери информацию о продукте:

**А. Главная страница:**

**Б. Страница цен:**

Извлеки: тарифы, цены, что входит в каждый план.

**В. Скриншот главной:**

**Г. Скриншот ключевой функции** (если есть демо/генератор):

- `scripts/screenshot.sh` — скриншоты сайтов

Это жёсткое правило без исключений.

## ПРЕДВАРИТЕЛЬНАЯ ПРОВЕРКА: Дубли на площадке (БЛОКИРУЮЩИЙ ШАГ)

> **КРИТИЧНО:** Дзен и другие RSS-площадки автоматически помечают статьи как «Дублированный контент» если они слишком похожи на уже опубликованные на том же канале. Такие статьи НЕ показываются в ленте — это полная потеря работы.

**Перед написанием КАЖДОЙ статьи для WordPress-площадок:**

1. Выдели 3-5 ключевых слов из заголовка новой статьи и поищи существующие посты по каждому:
```bash
source config.env
# Для каждого ключевого слова — отдельный поиск
curl -s "${WP_XXX_URL}/wp-json/wp/v2/posts?search=КЛЮЧЕВОЕ_СЛОВО&per_page=20&_fields=id,title&status=publish" \
  -u "${WP_XXX_USER}:${WP_XXX_PASS}" --insecure
```
Например, для статьи «Расстановка мебели онлайн» ищи: `search=мебель`, `search=расстановка`, `search=интерьер онлайн`.

2. Собери все найденные статьи — это потенциальные дубли

3. Если найдены статьи с похожей темой — скачай их контент и прочитай:
```bash
curl -s "${WP_XXX_URL}/wp-json/wp/v2/posts/[ID]?_fields=content" -u ... --insecure
```

4. Убедись что новая статья **принципиально отличается**:
   - Другой угол подачи (не просто перефразировка)
   - Другая структура H2/H3
   - Уникальные подтемы, которых нет в существующих статьях
   - Блоки про продукт написаны **разными словами** (не копипаст одних и тех же фраз)
   - Вступление и заключение **полностью уникальны**

5. Если тема слишком близка к существующей — **ОТКАЖИСЬ** и сообщи пользователю.

## ЭТАП 1: Сбор семантики через Wordstat MCP

### 1.1 Подготовь маркерные запросы

На основе темы статьи сгенерируй 5-10 маркерных запросов — ядро будущей статьи:
- Основной запрос (то, под что пишем статью)
- Вариации основного запроса
- Информационные: «как», «что такое», «почему»
- Коммерческие: «купить», «цена», «заказать» (если тема коммерческая)
- Сравнительные: «лучший», «vs», «сравнение»

### 1.2 Проверь частотность через Wordstat MCP

Для каждого маркерного запроса используй MCP-инструмент `mcp__wordstat__wordstat_get_top_requests`:
1. Передай запрос -> получишь **базовую частотность** + **вложенные запросы** + **похожие запросы** (LSI)
2. Для 3-5 самых важных вложенных запросов вызови повторно — собери глубокую семантику
3. Похожие запросы из ответа — это готовые LSI-слова для текста

Для оценки сезонности используй `mcp__wordstat__wordstat_get_dynamics`:
- Передай основной запрос -> получишь историю показов по месяцам
- Определи: запрос растёт, падает или стабилен
- Определи лучшее время для публикации

При необходимости проверь географию запроса через `mcp__wordstat__wordstat_get_regions`.

**Классификация частотности:**
- ВЧ: >5000/мес — высокая конкуренция, долго ждать результат
- СЧ: 500-5000/мес — золотая середина
- НЧ: 50-500/мес — быстрые результаты, низкая конкуренция
- МЧ: <50/мес — для кластерных страниц

### 1.3 Определи целевой запрос и кластер

Выбери **основной запрос** статьи (обычно СЧ) и собери вокруг него кластер из 5-15 дополнительных запросов, которые будут органично вписаны в текст.

```
ЦЕЛЕВОЙ ЗАПРОС: [запрос] ([частотность])
КЛАСТЕР:
  - [запрос2] ([частотность])
  - [запрос3] ([частотность])
  ...
LSI (связанные понятия): [слова]
```

## ЭТАП 2: Анализ конкурентов в ТОПе

**Это самый важный этап.** Нельзя написать статью лучше конкурентов, не зная что они написали.

### 2.1 Найди конкурентов

Используй web_search с основным запросом. Открой **топ-5 результатов** (не считая: маркетплейсы, видео, агрегаторы-мусор, wikipedia если это не информационная ниша).

Для каждого конкурента зафиксируй:

```
КОНКУРЕНТ #[N]: [URL]
Тип сайта: [медиа / блог бренда / экспертный блог / агрегатор]
```

### 2.2 Анализ структуры и интента

Для каждой статьи конкурента:

**А. Интент (что хочет пользователь):**
- Информационный — узнать что-то
- Коммерческий — выбрать / купить
- Транзакционный — совершить действие

**Б. Структура статьи:**
- Заголовок H1: как сформулирован
- Структура H2/H3: какие подтемы раскрыты
- Есть ли: таблицы, списки, FAQ, сравнения, примеры
- Где стоит главный ответ: в начале или в конце

**В. Гэпы — чего НЕ хватает:**
- Вопросы пользователя, которые статья НЕ закрывает

- Нет практических примеров / цифр / кейсов
- Нет скриншотов / визуалов (наш козырь!)

## ЭТАП 2.5: Сбор и верификация фактуры

**Критически важный этап.** Статья не должна быть пересказом конкурентов или фантазией модели. Каждый факт, цифра и утверждение — из проверенного источника.

### Принцип: НЕ ЗНАЕШЬ — ИЩИ, НЕ НАШЁЛ — НЕ ПИШИ

Claude НЕ должен выдумывать:
- Цены сервисов и тарифы
- Статистику и исследования (McKinsey, Houzz, Grand View Research и т.д.)
- Количество пользователей, рейтинги, даты запуска
- Технические характеристики продуктов
- Юридические нормы и номера статей законов

### 2.5.1 Составь список фактов для проверки

Перед написанием пройдись по плану статьи и выпиши ВСЕ фактические утверждения, которые потребуются:

```
ФАКТЫ ДЛЯ ПРОВЕРКИ:
|-- Цены: [список сервисов, чьи цены нужны]
|-- Статистика: [какие цифры/исследования хотим привести]
|-- Функционал: [что именно умеет каждый продукт]
|-- Доступность: [работает ли без VPN, какие карты принимает]
`-- Тренды/прогнозы: [нужны ли ссылки на исследования]
```

### 2.5.2 Проверяй через первоисточники

Для каждого факта — отдельный `WebSearch` + `WebFetch` по первоисточнику:

**Цены и тарифы:**
- Открой официальный сайт сервиса через `WebFetch` -> страница /pricing
- НЕ бери цены из обзоров конкурентов — они могут быть устаревшими
- Если цена не найдена — напиши «цены уточняйте на сайте» вместо выдумки

**Статистика и исследования:**
- `WebSearch` по точному названию исследования + год
- `WebFetch` на страницу-первоисточник (отчёт, пресс-релиз)
- Если исследование не находится — НЕ ЦИТИРУЙ ЕГО. Лучше без цифры, чем с выдуманной
- Допустимо: «по данным [источник]» — только если источник реально найден и прочитан

**Функционал продуктов:**
- `WebFetch` на главную страницу / страницу features каждого сервиса
- Проверяй: реально ли работает из России, есть ли русский язык, какие функции доступны бесплатно
- Скриншот страницы = доказательство (ЭТАП 5)

**Юридическая информация:**
- `WebSearch` по номеру статьи / названию закона
- Только проверенные формулировки, без вольных трактовок

### 2.5.3 Реестр проверенных фактов

Зафиксируй результат проверки:

```
ПРОВЕРЕННЫЕ ФАКТЫ:
| Факт                         | Источник (URL)                | Статус       |
|------------------------------|-------------------------------|--------------|
| [Продукт]: [тариф/цена]     | [сайт]/pricing                | проверено    |
| McKinsey: 34% студий юзают AI| НЕ НАЙДЕН                     | убрать       |
| ReRoom: нет русского языка   | reroom.ai (проверено WebFetch)| проверено    |
```

### 2.5.4 Правила работы с фактами

1. **Нашёл первоисточник** -> используй, ставь ссылку или указывай «по данным [X]»
2. **Нашёл в нескольких обзорах, но не в первоисточнике** -> используй осторожно, без конкретных цифр. «По оценкам экспертов» вместо «по данным McKinsey, 34%»
3. **Не нашёл нигде** -> НЕ ПИШИ. Лучше убрать абзац, чем выдумать факт
4. **Нашёл, но данные старые** -> укажи год: «по данным X на 2024 год» — читатель сам оценит актуальность
5. **Цены** -> всегда указывай «на [месяц год]» — цены меняются

| Отзывы пользователей | Trustpilot, Product Hunt, отзовики через `WebSearch` |

## ЭТАП 5: Генерация изображений

> **КРИТИЧНО: Генерация картинок — ТОЛЬКО через bash-скрипты!**
> ```bash
> bash scripts/generate-image.sh cover|image|notext ...
> bash scripts/screenshot.sh ...
> ```
> **НЕ использовать MCP-инструменты** для генерации изображений (nano_banana_pro, flux2-pro, seedream, grok-imagine, pexels и др.) — они ЗАПРЕЩЕНЫ.
> Если скрипт `generate-image.sh` выдаёт ошибку — покажи её пользователю. НЕ пропускай генерацию обложки. НЕ диагностируй как «ключ истёк» без проверки.
> Скрипт ищет config.env автоматически (../config.env от себя). Запускай через абсолютный путь или из директории скилла.

Все изображения генерируются через **Nano Banana 2** (`nano-banana-2`). Приоритет моделей в скрипте: `nano-banana-2` -> `gemini-3-pro-image-preview` -> `gemini-2.5-flash-image`. Скрипт автоматически retry 3 раза на каждой модели перед переключением. Другие модели (gpt-4o-image, gpt-image-1 и т.д.) ЗАПРЕЩЕНЫ.

### 5.1 Обложка статьи (ОБЯЗАТЕЛЬНО)

Обложка создаётся всегда. Содержит заголовок статьи на русском языке.

```bash
bash scripts/generate-image.sh cover \
  "<визуальный промпт — описание сцены на английском>" \
  "<заголовок статьи на русском>" \
  "<slug-статьи>"
```

**Пример:**
```bash
bash scripts/generate-image.sh cover \
  "Modern living room with AI interior design visualization, soft natural light, Scandinavian style, photorealistic" \
  "Как ИИ меняет дизайн интерьера в 2026 году" \
  "ai-interior-design-2026"
```

**Советы для промпта визуала:**
- Пиши на английском — модель лучше понимает визуальные описания на EN
- Указывай стиль: photorealistic / digital art / flat design / infographic
- Указывай освещение: soft natural light / studio light / dramatic shadows
- Указывай цветовую гамму: warm tones / cool blues / neutral palette
- Обложка должна отражать тему статьи — не просто красивая картинка

**ОБЯЗАТЕЛЬНО: Проверка текста на обложке.**

После генерации обложки скачай файл, валидируй (`file` + `ls -la` — должен быть >10KB и "image data"), и только затем открой через Read tool. Прочитай текст на картинке **посимвольно**. Нейросети часто искажают русский текст: пропускают буквы, меняют порядок, добавляют мусорные символы. Если текст искажён — **перегенерируй** обложку (может потребоваться 2-3 попытки). НЕ вставляй обложку с битым текстом в статью.

**ОБЯЗАТЕЛЬНО: Проверка AI-иллюстраций на соответствие подписям.**

После генерации каждой AI-иллюстрации скачай, валидируй (`file` + `ls -la`), и только затем открой через Read tool. Проверь:
- **Содержание картинки соответствует подписи** — если подпись говорит «тот же дом до и после», на картинке должен быть один и тот же дом (та же форма, этажность, пропорции), а не два разных здания
- **Нет логических противоречий** — если описано «слева исходный, справа визуализация», это должен быть реально тот же объект в разных стилях
- **Нейросети склонны генерировать два разных объекта** вместо одного «до/после» — это частая ошибка. Если результат не соответствует описанию — перегенерируй с уточнённым промптом или замени подпись так, чтобы она точно описывала то, что на картинке

НЕ вставляй иллюстрацию с подписью, которая не соответствует содержанию картинки.

### 5.2 Скриншоты упомянутых сервисов

**Рекомендуется снимать через сервер** (см. «Справочник: Скрипты изображений -> Скриншоты через сервер»). Локальный `screenshot.sh` часто таймаутит — сайты грузятся медленно или блокируют зарубежный IP. Через сервер (русский IP) — быстрее и надёжнее, плюс можно закрывать попапы.

Локальный скрипт — только если одиночный скриншот и сайт быстро отвечает:

```bash
bash scripts/screenshot.sh \
  "https://url-сервиса.ru" \
  "название-сервиса" \
  1280 800
```

**Правила скриншотов:**
- Снимай главную страницу или страницу с ключевой функцией
- Если сервис требует авторизацию — снимай лендинг/главную
- Alt-текст: «Скриншот [название сервиса] — [что показано]»
- Подпись под скриншотом: поясни что именно показано на экране

### 5.2.1 Проверка качества скриншотов (БЛОКИРУЮЩИЙ ШАГ)

**НЕЛЬЗЯ переходить к написанию статьи без проверки КАЖДОГО скриншота.** Скачай файл с сервера и проверь его.

**КРИТИЧНО: Перед открытием изображения через Read tool — ОБЯЗАТЕЛЬНО валидируй файл:**
```bash
# 1. Проверь что файл существует и не пустой (минимум 10KB для скриншота)
ls -la /tmp/screenshot.png
# 2. Проверь что это валидное изображение
file /tmp/screenshot.png  # должно показать "PNG image data" или "JPEG image data"
# 3. Проверь размеры
sips -g pixelWidth -g pixelHeight /tmp/screenshot.png  # должны быть разумные размеры (>100px)
```
**Если файл < 10KB, `file` не показывает "image data", или sips выдаёт ошибку — НЕ ОТКРЫВАЙ через Read tool!** Битое изображение сломает весь контекст разговора (API Error: "Could not process image"), и сессия станет неработоспособной. Вместо этого пересними скриншот или используй фоллбэк (поиск скриншота в сети).

**Что проверять:**
- Cookie-баннеры / consent-попапы (Termly, OneTrust, CookieBot и др.)
- Cloudflare challenge / капча ("Verify you are human")
- Ошибки 502/503/404
- Модальные окна, рекламные баннеры, попапы подписки
- Пустая или не загрузившаяся страница

**Если скриншот с дефектом — действуй по приоритету:**

1. **Cookie-попап / баннер** -> пересними через сервер с закрытием попапа:
   ```bash
   ssh -i "$SSH_KEY_PATH" "${SSH_USER}@${SSH_HOST}" 'NODE_PATH=$(npm root -g) node -' << 'EOF'
   // ... page.goto -> page.click("button:has-text('Понятно')") -> screenshot
   EOF
   ```
   Или удали попап через `page.evaluate()` — найди элемент по тексту (`textContent.includes("cookie")`) и вызови `el.style.display = "none"`.

2. **Cloudflare challenge / капча** -> автоматически не обходится. Ищи скриншот интерфейса в обзорных статьях через WebSearch + WebFetch (ищи `img src` в статьях-обзорах сервиса), скачай `curl -L -o /tmp/service.jpg "URL"` и загрузи на сервер через `scp`.

3. **Ошибка 502/гео-блок** -> сними через сервер (SSH + Playwright, русский IP). Если сайт лежит целиком — ищи скриншот в обзорных статьях (фоллбэк как п.2).

4. **Промо-баннер / модальное окно** -> пересними с `page.evaluate()` — удали элемент точечно по тексту. **Не удаляй все fixed/sticky элементы** — это уберёт и навбар. Удаляй только по конкретному тексту или классу.

5. **Ничего не помогает (таймаут, Cloudflare, гео-блок, 502)** -> **ОБЯЗАТЕЛЬНО** найди скриншот интерфейса в сети. Это не опциональный шаг — статья без скриншота сервиса выглядит пустой.

**Поиск скриншотов в сети (ОБЯЗАТЕЛЬНЫЙ фоллбэк):**

Если автоматический скриншот не удался по любой причине — ищи готовый скриншот:

```
1. WebSearch: "[название сервиса] обзор скриншот интерфейс" или "[service name] review screenshot interface"
2. WebFetch обзорной статьи -> извлеки img src URL скриншотов интерфейса
3. Скачай лучший вариант: curl -L -o /tmp/service-screenshot.png "URL"
4. Валидируй файл перед просмотром: `file /tmp/service-screenshot.png` (должно быть "image data") + `ls -la` (>10KB). Только после этого проверяй визуально через Read tool
5. Обрежь ненужное (строка браузера, панели, лишние элементы) через sips или imagemagick:
   # Обрезка сверху (например убрать 80px панели браузера):
   sips --cropOffset 80 0 --cropToHeightWidth HEIGHT WIDTH /tmp/service-screenshot.png
   # Или через imagemagick на сервере:
   ssh ... "convert input.png -crop WxH+0+80 +repage output.png"
6. Загрузи на сервер: scp -i "$SSH_KEY_PATH" /tmp/service-screenshot.png ${SSH_USER}@${SSH_HOST}:${SERVER_IMG_PATH}/
7. Очисти метаданные: ssh ... "exiftool -all= -overwrite_original /path/to/file.png"
```

**Правило: у КАЖДОГО упомянутого сервиса ДОЛЖЕН быть скриншот.** Если в статье 10 сервисов — должно быть 10 скриншотов (+ обложка + иллюстрации). Нельзя пропустить сервис без скриншота только потому что автоматический снимок не получился.

**Скрипт screenshot.sh НЕ закрывает попапы автоматически.** Для закрытия попапов снимай через сервер напрямую (SSH + inline Node.js + Playwright), где можно добавить `page.click()` и `page.evaluate()`.

### 5.3 Иллюстрации к разделам

**С текстом** (когда раздел можно подписать кратко — до 40 символов):
```bash
bash scripts/generate-image.sh image \
  "<визуальный промпт>" \
  "<текст на русском — подпись/заголовок иллюстрации>" \
  "<slug-иллюстрации>" \
  "16:9"
```

**Без текста** (когда иллюстрация говорит сама за себя):
```bash
bash scripts/generate-image.sh notext \
  "<визуальный промпт>" \
  "<slug-иллюстрации>" \
  "16:9"
```

**Соотношения сторон для иллюстраций:**
| Формат | Ratio | Когда использовать |
|--------|-------|-------------------|
| Широкий | `16:9` | Стандарт для статей, схемы, сцены |
| Квадрат | `1:1` | Иконки, портреты, логотипы |
| Портретный | `2:3` | Вертикальные инфографики |
| Инфографика | `1:4` | Длинные вертикальные схемы |

### 5.4 Правила текста на изображениях (русский язык)

Nano Banana 2 хорошо рендерит русский текст, но есть нюансы:

- **Лаконично**: заголовок/подпись до 40 символов — чёткий рендер
- **Длинный текст**: скрипт автоматически разбивает на строки по 25 символов
- **Обложка**: заголовок статьи — полностью, даже длинный (модель сама переносит строки)
- **Иллюстрации**: краткая подпись, не пересказ раздела

## ЭТАП 6: Написание статьи

### Под Яндекс (YATI)

- **Полнота темы > плотность ключей**: YATI «читает» весь текст и оценивает экспертность
- **Нет воды**: Каждое предложение несёт смысл
- **LSI органично**: Синонимы, профессиональная лексика, связанные понятия
- **Баден-Баден**: Плотность ключей <=2-3%. Запрещены повторы в конце каждого абзаца
- **Структура удерживает читателя**: Логика повествования -> хорошие поведенческие сигналы

### Под Google (E-E-A-T + GEO)

- **Experience**: «Мы протестировали», «в нашей практике», конкретные цифры
- **Expertise**: Ссылки на исследования, данные, первоисточники
- **Answer First**: Главный ответ — первое предложение после H2 (для AI Overviews)
- **Fact Density**: Максимум цифр, статистики, дат — AI-модели цитируют факты
- **Форматирование для AI**: Таблицы, списки — AI легко «достаёт» структурированные данные

### Вставка изображений в текст

**Обложка статьи:**
- **WordPress (Дзен-блоги, ПУТЬ 1):** обложка устанавливается ТОЛЬКО как `featured_media` через WP API. В HTML-теле статьи обложку **НЕ вставлять**. Статья начинается сразу с текста вступления.
- **MDX/HTML (блог на сайте, ПУТЬ 2/3):** обложка вставляется сразу после H1:
```markdown
# Заголовок статьи

![Заголовок статьи — краткое описание](https://your-server.ru/img/articles/cover.png)

Первый абзац статьи...
```

**Скриншот сервиса** — сразу после первого упоминания, с подписью:
```markdown
[Пример упоминания продвигаемого продукта — возьми из профиля проекта (projects/*.md),
поле "Как упоминать в статьях". Первое упоминание — во 2-3 абзаце.]

![Скриншот главной страницы [продукт]](https://your-server.ru/img/articles/product-screenshot.png)
*[Подпись из профиля проекта]*
```

**AI-иллюстрация к разделу** — после заголовка H2, перед текстом:
```markdown
## Как выбрать стиль интерьера

![Примеры стилей интерьера — скандинавский, лофт, минимализм](https://your-server.ru/img/articles/styles.png)

Выбор стиля начинается с...
```

### Универсальные правила текста

| Параметр | Правило |
|----------|---------|
| Длина | **Минимум 2500 слов** (жёсткий порог). На 20-30% длиннее среднего топ-3 — но не менее 2500 слов в любом случае. |
| Абзацы | 40-60 слов, одна мысль |
| H2 заголовки | Вопрос или конкретное утверждение |
| Таблицы | Любое сравнение 3+ строк |
| FAQ | Минимум 4-6 вопросов точными формулировками |
| Изображения | 1 на каждые 300-400 слов текста |

### Анти-паттерны

- «В современном мире всё больше людей...» — водяное вступление
- Ключевые слова через запятую
- Пустые заключения («Надеемся, статья была полезной»)
- Слово «Заключение» — выдаёт ИИ-контент. Используй: «Что выбрать: итоги», «Подведём итог», «Резюме» и т.п.
- Копирование структуры конкурента дословно
- Отсутствие конкретики («это сложно» -> «это занимает 3-5 дней»)
- Изображение без alt-текста и подписи
- Скриншот без контекста (всегда объясняй что показываешь)
- Дублирование ссылки: «Продукт (site.ru)» — если есть гиперссылка `<a>`, не дублируй URL в скобках
- HTML-таблицы (`<table>`) — Дзен, Pikabu, РБК не поддерживают. Используй списки или картинку

### 8.1.1 Проверка уникальности обложки на площадке (WordPress)

> **ОБЯЗАТЕЛЬНО для WordPress-площадок.** При параллельной работе нескольких агентов на одном WP возможны коллизии: один агент загружает обложку, а другой привязывает чужую media_id к своему посту. Результат — одинаковые обложки на разных статьях, что убивает CTR в Дзене.

После установки `featured_media` на пост — **проверь что обложка уникальна:**

```bash
source config.env
# Получи featured_media текущего поста
MY_MEDIA_ID=[ID обложки этого поста]

# Проверь что этот media_id НЕ используется другими постами
curl -s "${WP_URL}/wp-json/wp/v2/posts?per_page=50&_fields=id,featured_media,title&status=publish" \
  -u "${WP_USER}:${WP_PASS}" --insecure | python3 -c "
import sys, json
posts = json.load(sys.stdin)
dupes = [p for p in posts if p['featured_media'] == ${MY_MEDIA_ID}]
if len(dupes) > 1:
    print('ДУБЛЬ ОБЛОЖКИ! media_id=${MY_MEDIA_ID} используется в:')
    for p in dupes:
        print(f'  post_id={p[\"id\"]} — {p[\"title\"][\"rendered\"][:60]}')
else:
    print('Обложка уникальна')
"
```

**Если обнаружен дубль:** перегенерируй обложку, загрузи как новый media, привяжи к посту. НЕ оставляй одинаковые обложки на разных статьях.

### ПУТЬ 1: WordPress API (Дзен-блоги)

Используется для Дзен-блогов. Статья публикуется напрямую в WordPress, откуда автоматически экспортируется в Дзен через RSS.

**Определи блог из профиля проекта** (`projects/*.md`, секция "Площадки и WordPress") — там указаны WP-переменные (`WP_XXX_URL`, `WP_XXX_USER`, `WP_XXX_PASS`).

**Шаг Б1: Подготовь HTML-контент**

Контент для WordPress — чистый HTML без `<!DOCTYPE>`, `<head>`, `<style>`. Только содержимое `<body>`:
- Заголовки: `<h2>`, `<h3>`
- Абзацы: `<p>`
- Списки: `<ul>`, `<ol>`
- Картинки: `<img src="[URL с сервера изображений]" alt="[описание]">`
- Подписи: `<em>[подпись]</em>`
- **Никаких `<table>`** — списки или картинки
- URL картинок — прямые ссылки с вашего сервера изображений

**Шаг Б2: Проверь дубли и создай пост как ЧЕРНОВИК**

> **КРИТИЧНО: WordPress -> RSS -> Дзен происходит МГНОВЕННО для статусов `publish`.**
> **Публикуй ТОЛЬКО ОДИН РАЗ и ТОЛЬКО ПОСЛЕ того как обложка прикреплена.**
> Удалить из Дзена потом НЕВОЗМОЖНО — даже если удалить пост из WordPress.
>
> **ОБЯЗАТЕЛЬНЫЙ ПОРЯДОК:**
> 1. Создай пост со статусом `draft` (черновик — не попадает в RSS)
> 2. Прикрепи обложку (`featured_media`)
> 3. Переведи в `publish` — ТОЛЬКО ОДИН РАЗ
>
> **Если пост с таким заголовком уже существует — ОБНОВИ его (PUT), НЕ создавай новый (POST).**

## Справочник: Wordstat MCP

MCP-сервер `wordstat` подключён через коннектор (mcp-kv.ru). Содержит инструменты для работы с Яндекс Wordstat.

### Инструменты

| MCP-инструмент | Что делает | Когда использовать |
|----------------|------------|-------------------|
| `mcp__wordstat__wordstat_get_top_requests` | Частотность запроса + вложенные запросы + похожие запросы (LSI) | **Основной инструмент.** Для каждого маркерного запроса и для раскрытия глубокой семантики |
| `mcp__wordstat__wordstat_get_dynamics` | История показов запроса по месяцам | Определить сезонность и тренд (растёт/падает/стабилен) |
| `mcp__wordstat__wordstat_get_regions` | Распределение запроса по регионам | Определить геотаргетинг, понять где запрос популярнее |
| `mcp__wordstat__wordstat_get_regions_tree` | Дерево регионов (иерархия) | Для структурированного регионального анализа |
| `mcp__wordstat__wordstat_get_user_info` | Информация о пользователе Wordstat | Проверить доступность сервиса и лимиты |

### Типовой workflow сбора семантики

```
1. wordstat_get_top_requests("основной запрос")
   -> частотность, вложенные, похожие
2. wordstat_get_top_requests("важный вложенный 1")
   -> глубокая семантика
3. wordstat_get_top_requests("важный вложенный 2")
   -> ещё глубже
4. wordstat_get_dynamics("основной запрос")
   -> сезонность
5. wordstat_get_regions("основной запрос")  [опционально]
   -> география
```

> Если Wordstat MCP недоступен — используй web_search для оценки популярности запросов или запроси у пользователя данные по семантике.

## Справочник: Скрипты изображений

Скрипты находятся в `scripts/`. Конфиг: `config.env` (создай из `config.env.example`).

**Модель:** `nano-banana-2` (основная) -> `gemini-3-pro-image-preview` -> `gemini-2.5-flash-image` (фоллбеки) через ApiYi

| Скрипт | Режим | Назначение |
|--------|-------|-----------|
| `screenshot.sh <URL> <slug> [w] [h]` | -- | Скриншот сайта -> SSH -> сервер |
| `generate-image.sh cover "<визуал>" "<заголовок RU>" <slug>` | cover | Обложка с заголовком на русском, 16:9 |
| `generate-image.sh image "<визуал>" "<текст RU>" <slug> [ratio]` | image | Иллюстрация с подписью на русском |
| `generate-image.sh notext "<визуал>" <slug> [ratio]` | notext | Иллюстрация без текста |

**ВАЖНО: NVM и PATH**

Скрипты используют `node` и `npm`, но в неинтерактивном шелле NVM не загружен и `node` не найден. **Перед каждым вызовом скрипта** убедись что `node` доступен:

```bash
# Вариант 1: Если используешь NVM — добавь путь к node в PATH
export PATH="$(dirname $(which node)):$PATH"

# Вариант 2: Укажи путь к NVM напрямую (подставь свою версию node)
export PATH="$HOME/.nvm/versions/node/$(node -v 2>/dev/null || echo v20.0.0)/bin:$PATH"

# Затем запускай скрипт
bash scripts/screenshot.sh "https://example.com" "example" 1280 800
```

**Возможные ошибки и решения:**
- `node: command not found` -> не загружен NVM, добавь PATH (см. выше)
- `config.env не найден` -> скопируй `config.env.example` -> `config.env`, заполни
- `playwright не установлен` -> установи вручную: `npm install playwright && npx playwright install chromium`
- `SSH: Permission denied` -> проверь `SSH_KEY_PATH`, права на ключ: `chmod 600 ~/.ssh/id_rsa`
- `API error 401` -> проверь `APIYI_API_KEY` в config.env
- `API не вернул изображение` -> добавь в промпт префикс "Generate an image:" или увеличь timeout
- Текст на картинке нечёткий -> сократи текст до 25 символов, используй режим `image`
- Скриншот показывает 502/гео-блок -> сними через сервер (см. ниже)
- Cloudflare challenge на скриншоте -> найди скриншот в обзорных статьях (WebSearch -> WebFetch -> curl -> scp)

**Скриншоты через сервер (рекомендуется для массовых скриншотов):**

`screenshot.sh` снимает с локального мака. Если сайт блокирует, таймаутит или отдаёт 502 — снимай **через сервер** (русский IP, playwright установлен):

```bash
source config.env
ssh -i "$SSH_KEY_PATH" "${SSH_USER}@${SSH_HOST}" 'NODE_PATH=$(npm root -g) node - << '\''NODEOF'\''
const { chromium } = require("playwright");
(async () => {
  const browser = await chromium.launch({ args: ["--no-sandbox"] });
  const ctx = await browser.newContext({ viewport: { width: 1280, height: 800 } });
  const page = await ctx.newPage();
  await page.goto("[URL]", { waitUntil: "domcontentloaded", timeout: 30000 });
  await page.waitForTimeout(3000);
  // Закрытие попапов по тексту кнопки
  for (const sel of ["button:has-text(\"Понятно\")", "button:has-text(\"Accept\")", "button:has-text(\"OK\")"]) {
    try { await page.click(sel, { timeout: 500 }); } catch {}
  }
  await page.waitForTimeout(1000);
  await page.screenshot({ path: "${SERVER_IMG_PATH}/[slug]-screenshot.png" });
  await browser.close();
  console.log("OK");
})().catch(e => { console.error(e.message); process.exit(1); });
NODEOF'
```

Для массовых скриншотов (8+ сервисов) — заверни в цикл по массиву `[[url, slug], ...]` в одном Node.js-скрипте, чтобы не создавать браузер для каждого URL.

**Очистка метаданных (ОБЯЗАТЕЛЬНО для всех картинок):**

После загрузки любых картинок на сервер — очисти метаданные. Это удаляет C2PA маркеры, SynthID водяные знаки ("Created by Google Generative AI"), EXIF, XMP, IPTC:


Если `exiftool` не установлен: `ssh ... "apt-get install -y libimage-exiftool-perl"`

## Справочник: Требования площадок

### РБК (rbc.ru)

| Параметр | Требование |
|----------|-----------|
| Макс. длина текста | **15 000 символов** (с пробелами) |
| Обложка | Формат **16:10**, файл **JPG** |
| Картинки в тексте | Формат **JPG** |
| Заголовок | До **73 символов** |

**Важно при написании для РБК:**
- Планируй объём заранее — 15 000 символов это ~2000-2500 слов
- Если тема требует больше — сокращай: убирай наименее ценные разделы, объединяй похожие пункты, режь воду
- Обложку генерируй в соотношении 16:10 (например 1600x1000)
- Перед финализацией проверь длину: `wc -m < article.html` или посчитай в редакторе

**Конвертация PNG->JPG (только для РБК):**

Скрипты `generate-image.sh` и `screenshot.sh` генерируют PNG. Для РБК нужен JPG. После генерации всех картинок конвертируй на сервере:

```bash
# Если imagemagick установлен:
ssh -i "$SSH_KEY_PATH" "${SSH_USER}@${SSH_HOST}" "cd ${SERVER_IMG_PATH} && convert image.png -quality 90 image.jpg"

# Массовая конвертация всех скриншотов:
ssh ... "cd ${SERVER_IMG_PATH} && for f in *-screenshot.png; do convert \"\$f\" -quality 90 \"\${f%.png}.jpg\"; done"

# Если imagemagick нет — установить:
ssh ... "apt-get install -y imagemagick"

# Или скачать на мак, конвертировать sips'ом и загрузить обратно:
sips -s format jpeg -s formatOptions 90 image.png --out image.jpg
scp -i "$SSH_KEY_PATH" image.jpg ${SSH_USER}@${SSH_HOST}:${SERVER_IMG_PATH}/
```

После конвертации не забудь очистить метаданные: `exiftool -all= -overwrite_original *.jpg`

В HTML статьи используй пути к `.jpg` файлам, не к `.png`.
